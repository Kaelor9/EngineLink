# EngineLink 0.16.6 — Wi-Fi 2.0 Stages 1–3 (development and bench build)

**Status: *built* (pinned toolchain, host tests and source checks pass),
partially tested on actual hardware as of 2026-11-06; not fully bench-verified
or boat-verified. Not a release:** no merge to `main`, no
GitHub Release, not offered under "Check for updates". It is a bench build
for the owner. Wi-Fi 2.0 as a whole ships as 0.17.0 after the bench and boat
protocol in [WIFI_REWRITE_PLAN.md](../WIFI_REWRITE_PLAN.md) 9.9 (D24).

What is in it (plan section 9):

- **Stage 1 — access point radio and diagnostics.** The own Wi-Fi again runs
  20 MHz, keeps quiet phones 600 s and uses country `DK` (802.11d on), all
  through Espressif's `esp_wifi` calls, as every version before 0.16.2 did.
  The transmit power is set after the country in both modes and checked
  exactly (the driver's unset 20 dBm no longer passes as 19.5). The report,
  `/api/diag` and the SD log show each joined phone's signal at EngineLink,
  its Wi-Fi standards and the access point's real channel, bandwidth, PMF,
  inactive time and country. Repeated router retries fold into one line.
  CI installs exactly Arduino core 3.3.12 and NeoPixel 1.15.5.
- **Stage 2 — web server.** Espressif's `esp_http_server` replaces the
  Arduino web server and the extra listeners on ports 81 and 82. It runs in
  its own task, so a phone that stops answering can no longer stall the main
  loop (the 5–10 s "web" stalls of 0.16.5). Downloads run in a separate
  transfer task, uncompressed (same routes, columns, file names and content).
  Security without a login: only EngineLink's own addresses are answered
  (421 otherwise), only its own pages may read replies (no more
  `Access-Control-Allow-Origin: *`), every change needs the app's
  `X-EngineLink` header (403 otherwise), request sizes are limited.
  Firmware upload sends the file as the request body and is checked for
  length, image header and application before it can start. A new firmware
  confirms itself only after a real web client got an answer (or the board's
  own request to itself, when no phone has connected); without that within
  10 minutes the board goes back to the previous firmware by itself.
- **Stage 3 — state machine.** The Wi-Fi 2.0 states (standalone, router
  test, router, router lost, return) as a host-tested header; **not used by
  the firmware yet**. The Wi-Fi behaviour (modes, fallback after 2 min,
  return every 10 min, router setup) is unchanged from 0.16.5.

Not changed: J1708 and KAD reading, NMEA 2000, trips, fuel, totals, storage
formats, NVS settings, the app's screens. Settings and data survive the
update.

## Second bench build (2026-11-06, after the first bench reports)

Same version number; the Wi-Fi report's first line shows the build time.
No Wi-Fi behaviour changed (no state machine, no network switch). Fixes for
what the reports showed (plan 12.1 I10, I11):

- **Engine reading no longer waits for the SD card.** Opening a file on a card
  with many logs takes 0.1–0.4 s; the SD info (7.3 s), the daily raw clean-up
  (485 ms a pass), the Wi-Fi log on the card (~300 ms) and the wipe did that
  while holding the engine lock. They now let it go while the card works.
  Settings shows the SD card's size from a count made in the background
  ("Reading the card…" for a moment after it opens). A card removed during a
  download stops the download first and is then unmounted; remount, wipe and
  factory reset say "busy, try again" for the moment the card is in use.
- The serial commands `wifi log` and `wifi reports` stop as soon as the
  computer stops reading (before: up to 2 s per 256 bytes), and the SD Wi-Fi
  log can no longer skip an event that arrives while it writes.
- **Report:** "Busy (503)" split by cause with the last path; the engine
  task's longest wait names the task that held the lock, with the number of
  waits over 100 ms and its longest round of its own work.
- The router name is hidden in the committed test files.

Not changed: storage formats, settings, the raw log and how it is written,
the update and rollback path. Status: *built*; not yet run on the board.

## Third bench build (2026-11-08, router mode)

- **Router mode joins at 20 MHz again and rides out 20 s without the
  router's beacons** (the driver's default is 6 s), as every version up to
  0.16.1 did. 0.16.2 dropped both. Reported 2026-11-08: on the router the app
  page (110 KB) failed after 20.5 s while small answers worked; plan 12.1
  I14. Standalone is unchanged.

Status: *built*; not yet run on the board.

## Install on the bench

Use **Settings › Firmware › Install from a file** with `enginelink-update.bin`
(keeps settings and data). Do not use the USB image (`*.merged.bin`): it
erases settings and data. After the restart, close and reopen the app (or
reload the page) so the phone loads the new app; the old app's requests
would be refused (403) by the new security check.

## Bench test (plan 9.1 and 9.2)

Do Stage 0 step 1 (plan 13.6) on 0.16.5 first if not done yet, and the
"before" downloads of the export check. Then, on 0.16.6, USB from a charger,
iPhone and PC on EngineLink Wi-Fi:

1. Within 2 min of the app reconnecting the Wi-Fi report says
   `Firmware self-test: passed (client response)`.
2. Wi-Fi report: `Access point as the driver runs it: channel 6, 20 MHz,
   … stations kept 600 s …, country DK`; `driver reports 19.50 dBm
   (78 quarter-dBm)`; each joined phone with its dBm.
3. App open on both for 30 min: no "Reconnecting"; report HTTP line
   `send failures` 0; longest loop part well under 1 s.
4. From the PC, the `curl` list in plan 9.2 (403 without the header, 421 for
   a foreign Host, 413 for a 3 KB body, no `Access-Control-Allow-Origin`
   for a foreign Origin, 20 parallel requests all 200).
5. Export check: download every export again and `diff` with the 0.16.5
   copies; no `Content-Encoding` header.
6. Install `enginelink-update.bin` once more from a file: restart and step 1
   again (tests the new upload path).
7. If a router is at hand: the report shows 19.50 dBm in router mode too;
   router switched off 2 min gives fewer than 10 event lines.

Send the Wi-Fi report after steps 1, 3 and 7, the `curl` output and the
`diff` result.
