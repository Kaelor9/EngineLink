# EngineLink v0.11.1 — Router interface lifecycle, retry safety and actionable diagnostics

## Why
Previous versions compiled correctly but the owner reports unstable router mode and very long web UI stalls. The code still used `WiFi.reconnect()` after 30 seconds without station association; on Arduino-ESP32 that API may first issue an explicit disconnect, potentially resetting an unfinished association. HTTP listener sockets were also left intact while AP/STA interfaces changed. These are plausible software defects, **not yet confirmed as the only root cause**.

## Normal operation
- **Standalone (factory default):** EngineLink's own Wi-Fi, HTTP at `192.168.4.1`, no external router.
- **Router (user choice):** AP disabled. Station connects to the selected **2.4 GHz** router, receives a DHCP address, and serves the same dashboard via that IP.
- **Failed router:** If no usable router IP is obtained for 120 seconds, a persisted rescue latch returns to standalone AP-only. The saved SSID/password remain available for another explicit attempt.
- **Provisioning:** The existing 2-pass 2.4 GHz discovery and manual SSID entry remain available in standalone mode; no automatic switch to the router without a user action.

## Corrections
- Replace the fallback `WiFi.reconnect()` with a non-forcing `esp_wifi_connect()` attempt after 30 seconds without STA association. That function does not deliberately disconnect the station from an in-progress session.
- Automatically close stale HTTP clients and rebind TCP port **80** after the AP starts or STA receives its router IP, in the main loop between requests. Separate workers independently rebind **81** (live telemetry) and **82** (throughput test) after the same interface-ready event.
- Record station association events and DHCP IP events independently, including measured time to association and time from association to receiving an IP.
- Preserve the last unexpected Wi-Fi error and the association-versus-DHCP failure stage **before** intentional fallback disconnects. Record those summary fields in NVS for later recovery diagnosis.
- Add a small, engine-independent `GET /api/network-health` endpoint, readable at either interface's IP, and display the new metrics in Diagnostics → Wi-Fi.
- Do not change the appearance of EngineLink, motor parsing, SD data, battery configuration or NMEA 2000.

## Hardware acceptance
1. Use the USB installer only after its manifest displays **v0.11.1**. Full USB install can overwrite internal NVS settings and history; prefer a firmware-only update when the existing installation permits it.
2. Verify factory standalone AP: connect a phone to EngineLink Wi-Fi and open `http://192.168.4.1/api/network-health`.
3. Choose the router SSID or type it manually; after the acknowledged switch, EngineLink AP must disappear. Determine the router-assigned IP from the router's DHCP client list.
4. Connect the phone to the router and open `http://<router-IP>/api/network-health` directly. Confirm `phase=online`, `associated=true`, a non-empty `ip`, and HTTP rebind count.
5. Open the complete dashboard via the same IP, use it for a sustained session, then temporarily restart the router; verify automatic reconnect and a new listener binding after router DHCP recovers.
6. Test incorrect credentials. After 120 seconds without router IP, rescue AP must appear and the health endpoint must show `failedReason`, `failedPhase` (1=association, 2=DHCP), and `failedAfterMs`. Note that a voluntary reason 8/36 during the subsequent mode switch is not the original router failure.
7. If the failure persists **even though** station association succeeds (a valid `dhcpMs` and address), inspect the TCP/HTTP path; if association fails with no successful IP events, focus on the actual Wi-Fi reason, antenna keep-out, 3.3-V supply stability and WPA2/WPA3/router configuration.

**Status:** The automated tests/ESP32-S3 build validate source and binary integrity, not real RF behavior. A real-device test is mandatory before calling this firmware stable.
